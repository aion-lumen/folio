Bar-Fix · warum die Bar bei 5/5 stehen blieb · was jetzt anders ist

Diagnose

Distinct mail_ids saturieren nach der ersten Voice (gemma) bei tranche_size. Voice 2 + 3 bringen keine neuen mail_ids — die Bar steht.

// vorher
const done = new Set(
  logs.filter(l => l.event_type === 'validated').map(l => l.mail_id)
).size;
const total = data.activeRun.tranche_size;        // = 5
return { done, total, unit: 'Mails' };

Fix (Variante A · heute aktiv)

Bar zählt Log-Zeilen (mail × voice combos). Bei 5 Mails × 3 Voices: 0 → 15. Unit „Stimmen" — wie LiveDetail.progressUnit es schon machte.

// jetzt
const done = logs.filter(l => l.event_type === 'validated').length;
const tSize = data.activeRun.tranche_size;
const total = tSize > 0 ? tSize * 3 : done;       // 3 Voices
return { done, total, unit: 'Stimmen' };

Resolved · ehemalige offene Frage zur Cascade-Doppelung

Resolved 2026-06-10 via Direktive D. Architekt hat den dritten Pfad gewählt: Cascade-Subprocess komplett aus production_worker.py entfernt. Worker macht ab jetzt nur noch Heuristik, der Validator-Run wird vom folio worker-runner als eigener Prozess gespawnt — race-frei via explizitem --mail-ids-Handoff aus den heuristik-Logs, verknüpft via neuer parent_run_uuid-Spalte. Decision-Doc: cascade-validator-cleanup-decision-2026-06-11.md, Implementation: fieldnote-direktive-d-pipeline-refactor-2026-06-10.md.

Historischer Stand (vor Direktive D) folgt unten als Archiv-Referenz.

Heutiger Zustand (vor D): Worker-Cascade läuft, beendet sich, dann läuft Auto-Validator nochmal über dieselben Mails. UPSERT macht das Ergebnis korrekt, aber 50% LLM-Compute ist Doppelarbeit (~10 min extra pro 5er-Tranche).

Mögliche Lösung (nicht in diesem Patch): in worker-runner/manager.ts:212 den Auto-Trigger überspringen, wenn cascade_ok im silent run vorkommt (oder generell skippen bei silent + cascade=true). Dazu müsste der Worker bei Cascade-Erfolg ein Signal hinterlassen, das der Manager liest.

Alternativ: die Cascade abschaffen und nur den Auto-Validator behalten — dann verliert man aber das „same run_uuid"-Pattern, das die Cascade in der UI klar als Worker-Teilphase erkennbar macht.

Architekten-Entscheidung. Datei: worker-runner/manager.ts:208–224 · production_worker.py:1086–1152.
